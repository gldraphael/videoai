## ADDED Requirements

### Requirement: Catalog Defines URL-Based Local Development Assets

The system SHALL use `devassets/catalog.yaml` as the tracked source manifest for
local development media, with each asset declaring only `id`, `title`, `type`,
and `source.url`.

#### Scenario: Developer defines local media

- **WHEN** a developer opens `devassets/catalog.yaml`
- **THEN** the catalog format supports `version: 1`
- **AND** each asset entry declares `id`, `title`, `type`, and `source.url`
- **AND** local file paths are not accepted as asset sources in this phase

#### Scenario: Seed validates catalog input

- **WHEN** the seed service reads an invalid catalog
- **THEN** it reports a clear validation error
- **AND** it writes an error setup status for the API and webapp to consume

### Requirement: Seed Service Runs In Local Compose

The system SHALL include `seed` as a first-class service in `compose.yaml` that
runs during local compose startup and prepares local media artifacts.

#### Scenario: Developer starts local compose stack

- **WHEN** a developer runs `podman compose up --build`
- **THEN** the seed service starts as part of the compose service graph
- **AND** the seed service uses a dedicated seed container image
- **AND** the webapp and API can start while seeding is still running

#### Scenario: Seed dependencies are containerized

- **WHEN** the seed service runs in the local compose stack
- **THEN** FFmpeg, ffprobe, `whisper.cpp`, `whisper-cli`, and a default Whisper
  model are available inside the seed container
- **AND** the default workflow does not require host-level media or
  transcription dependency setup

### Requirement: Seed Generates Local Media Library Artifacts

The seed service SHALL generate source media, audio, thumbnail, transcript, and
library index artifacts under gitignored runtime paths.

#### Scenario: Seed completes first setup

- **WHEN** the seed service processes a valid catalog with video assets
- **THEN** downloaded source media exists under `var/devassets/assets/`
- **AND** extracted audio exists for each processed video asset
- **AND** thumbnails exist under `var/thumbnails/`
- **AND** timestamped transcript files generated by `whisper.cpp` exist for
  each processed video asset
- **AND** `var/devassets/library.json` describes the generated media library

#### Scenario: Library references transcript files

- **WHEN** a developer inspects `var/devassets/library.json`
- **THEN** each transcribed asset includes a transcript reference
- **AND** the transcript reference includes the generated transcript path and
  format
- **AND** full transcript payloads are not embedded in `library.json`

### Requirement: Seed Reuses Existing Outputs When Catalog Identity Is Unchanged

The seed service SHALL treat the catalog identity as the deterministic hash of
asset `id` and `source.url` values only.

#### Scenario: Seed reruns without catalog identity changes

- **WHEN** the seed service runs after a successful setup
- **AND** the catalog identity hash is unchanged
- **AND** the required generated outputs still exist
- **THEN** the seed service exits successfully without downloading or
  regenerating media artifacts

#### Scenario: Metadata-only catalog update

- **WHEN** a developer changes an asset title without changing its `id` or
  `source.url`
- **THEN** the seed service updates generated library metadata as needed
- **AND** it does not re-download source media
- **AND** it does not regenerate thumbnails, audio, or transcripts solely
  because of the title change

#### Scenario: Asset source identity changes

- **WHEN** a developer changes an asset `id` or `source.url`
- **THEN** the seed service treats that asset identity as changed
- **AND** it regenerates required outputs for the changed asset identity

### Requirement: Seed Reports Setup Status Through Generated State

The seed service SHALL write setup status to `var/devassets/.seed/status.json`
so other services can observe setup progress and failures.

#### Scenario: Seed is running

- **WHEN** the seed service is actively preparing local assets
- **THEN** the generated status file reports a running state
- **AND** the status includes a human-readable setup message

#### Scenario: Seed completes successfully

- **WHEN** the seed service has generated or reused all required outputs
- **THEN** the generated status file reports a ready state
- **AND** the status includes the catalog identity hash and library path

#### Scenario: Seed fails

- **WHEN** the seed service cannot complete setup
- **THEN** the generated status file reports an error state
- **AND** the status includes a useful error message

### Requirement: API Exposes Devasset Readiness

The API service SHALL expose devasset readiness by reading generated seed status
and media library files.

#### Scenario: Webapp checks setup status

- **WHEN** the webapp requests the API devasset status endpoint
- **THEN** the API returns whether local devassets are missing, running, ready,
  or failed
- **AND** the API response includes the current setup message when available

#### Scenario: Library is ready

- **WHEN** `var/devassets/library.json` exists and seed status is ready
- **THEN** the API reports devassets as ready
- **AND** the API includes enough metadata for the webapp to continue to the
  normal local app experience

### Requirement: Webapp Shows Setup State Until Devassets Are Ready

The webapp SHALL show a local setup experience while devassets are being
prepared and only show the normal app experience once the API reports readiness.

#### Scenario: First local startup

- **WHEN** a developer opens the webapp before seeding has completed
- **THEN** the webapp shows a "Setting things up" state
- **AND** it continues checking devasset readiness through the API

#### Scenario: Devassets become ready

- **WHEN** the API reports devassets are ready
- **THEN** the webapp transitions from setup state to the normal app experience

#### Scenario: Seed setup fails

- **WHEN** the API reports a seed error
- **THEN** the webapp shows a setup error state with the available error message

### Requirement: Generated Library Writes Are Atomic

The seed service SHALL avoid exposing partially written setup status or media
library JSON to the API.

#### Scenario: API polls while seed writes output

- **WHEN** the API reads seed status or media library files while seed is
  updating them
- **THEN** it either reads the previous complete file or the next complete file
- **AND** it does not observe partially written JSON
